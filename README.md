# DEUSTO iDesign RES

This repository is an annual industrial electricity and thermal demand profile generator. The project builds high-resolution synthetic time series from normalized daily profiles, working calendars, seasonality, annual sectoral demand factors and weights extracted from **JRC-IDEES** workbooks.

The main goal is to generate realistic sub-hourly industrial load profiles for energy-system analysis when measured industrial consumption data is not available. The model supports different industrial sectors, European Union countries and shift-based operating patterns while preserving annual energy consistency.

## Project objective

The project aims to produce synthetic annual industrial electricity and heat demand profiles with a 15-minute resolution. These profiles are useful for energy-system studies, renewable-energy integration, industrial flexibility analysis, technology sizing and simulations where real measured load curves are not available.

The methodology separates two components:

1. **Temporal demand structure**: daily profiles by day type, calendar effects, work shifts, start-up/shutdown ramps and seasonality.
2. **Annual energy allocation**: sectoral weights, annual consumption values and scaling factors from external datasets.

This makes it possible to build a coherent temporal shape first and then scale it to the real annual consumption of the selected sector, country and year.

---

## Main features

- Generation of annual industrial electricity and thermal profiles.
- **15-minute** time resolution.
- Support for multiple European countries throughISO country codes.
- Industrial sector selection directly from `main.py`.
- Integration with **JRC-IDEES** data to obtain electrical weights by country, sector, and year.
- Electrical weighting modes:
  - `summed`: six aggregated electrical categories.
  - `unsummed`: detailed subsector or end-use rows extracted from IDEES workbooks.
  - `sfu`: standard final uses mode, if available in the local version of the code.
- Generation of `.xlsx` profiles with application/unit headers.
- Generation of stacked `.png` diagrams.
- Annual calendar logic with weekdays, Saturdays, Sundays, holidays, bridge days and constant-load periods.
- Intermediate normalization to **1000 MWh/year** before final scaling.
- Scaling to real annual consumption.
- Random fluctuations in mechanical loads to improve realism.
- Dedicated **work-shift** module for one-, two-, and three-shift industrial operation.

## What the code generates

When `python main.py` is executed, the project can generate:

1. **Annual load profiles** in Excel:
   - Written to `Generated/load_profiles/`.
   - Include one column per application or energy use.
   - Include a `Total` column.
   - Use a 15-minute datetime index.
   - Store units as `in kW`.

2. **Annual stacked diagrams** in PNG:
   - Written to `Generated/diagrams/`.
   - Show the contribution of each category to the total profile.
   - For electricity, the file name includes country, sector, year, and weighting mode.

3. **IDEES electrical weight workbooks**:
   - Generated by the helper scripts.
   - Available in aggregated (`summed`) or detailed (`unsummed`) format.

Example electrical diagram file names:

```text
iDesign_RES_ES_ISI_Iron_and_steel_2020_summed_Diagram.png
iDesign_RES_ES_ISI_Iron_and_steel_2020_unsummed_Diagram.png
```

Example electrical diagram titles:

```text
WZ08 ISI Iron and steel | ES | 2020 | unsummed
```

```python
os.environ.setdefault("IDESIGN_SHOW_PLOTS", "0")
```

Enables or disables electrical profile generation.


If `True`, the electrical pipeline runs.

#### `GENERATE_THERMAL_PROFILE`

Enables or disables thermal profile generation.

```python
GENERATE_THERMAL_PROFILE = False
```

If `True`, the thermal pipeline runs.

At least one of the two generation flags must be enabled.

Defines the country used for input data and output naming.

```python
COUNTRY_CODE = "FR"
```

The code is automatically converted to uppercase. It must be included in the `COUNTRY_CODES` dictionary.

#### `YEAR`

Defines the target year.

```python
YEAR = 2018
```

The year must be an integer. If some weight files do not contain the requested year, the code may fall back to the latest available year depending on the module.

#### `BASE_PATH`

Defines the project root path.

```python
BASE_PATH = PROJECT_ROOT
```

In most cases this should remain as `PROJECT_ROOT`.

#### `ELECTRICAL_INDUSTRY_NUMBER`

Selects the electrical industrial sector.

```python
ELECTRICAL_INDUSTRY_NUMBER = 6
```

The value is mapped through the `ELECTRICAL_INDUSTRIES` dictionary.

#### `ELECTRICAL_WEIGHTS_MODE`

Defines how JRC-IDEES electrical weights are read.


Available modes:

- `summed`: uses one sheet per sector with six aggregated electrical categories.
- `unsummed`: keeps detailed subsector/end-use rows from the IDEES extraction.
- `sfu`: standard final uses mode, if supported by the local implementation.

> Note: in some versions of the repository, `main.py` validates only `summed` and `unsummed`. If `sfu` is used, make sure the local code includes that mode in the validation and in the reader logic.

#### `THERMAL_INDUSTRY_NUMBER`

Selects the thermal industrial sector.

```python
THERMAL_INDUSTRY_NUMBER = 1
```

## General pipeline flow

The calculation flow is split into four main modules plus plotting/export:

```text
main.py
  ├── Profiles/LoadGeneratorElectricity.py
  │     ├── module_1: daily profile construction
  │     ├── module_2: peak/base factor adjustment
  │     ├── module_3: annual calendar, seasonality, normalization
  │     ├── module_4: annual scaling and electrical fluctuations
  │     └── module_plot: electrical diagram generation
  │
  └── Profiles/LoadGeneratorThermal.py
        ├── module_1: daily thermal profile construction
        ├── module_2: peak/base factor adjustment
        ├── module_3: annual calendar, seasonality, normalization
        ├── module_4: annual scaling
        └── module_plot: thermal diagram generation
```

The pipeline follows these steps:

1. Build daily profiles by day type.
2. Apply work-shift modulation.
3. Apply sector peak/base factors.
4. Build the annual calendar.
5. Apply seasonality.
6. Normalize the annual profile to 1000 MWh.
7. Scale it to real annual consumption.
8. Add electrical fluctuations, when applicable.
9. Save Excel profiles and PNG diagrams.

## How the modules work

### `Profiles/LoadGeneratorElectricity.py`

This file orchestrates the complete electrical generation process.

It cannot be executed directly. If run as a script, it stops and asks the user to run `python main.py` instead.

The `run(...)` function receives:

- `industry_number`,
- `industry_code`,
- `industry_name`,
- `year`,
- `base_path`,
- `country_code`,
- `weights_mode`.

It then performs the following sequence:

1. Calls `module_1.build_electric_daily_profiles(...)`.
2. Calls `module_2.apply_peak_base_factors(...)`.
3. Builds the annual calendar with `module_3.build_load_type_calendar(...)`.
4. Applies seasonality with `module_3.seasonality(...)`.
5. Normalizes to 1000 MWh with `module_3.normalising_1000(...)`.
6. Scales to annual consumption with `module_4.upscale_yearly(...)`.
7. Adds electrical fluctuations with `module_4.add_fluctuations(...)`.
8. Generates a summed or unsummed diagram with `module_plot`.
9. Writes the final profile to Excel.

The final Excel file is saved under:

```text
Generated/load_profiles/
```

with a name similar to:

```text
iDesign_RES_<industry_name>_<industry_code>-<country_code>.xlsx
```

### `Profiles/LoadGeneratorThermal.py`

This file orchestrates the thermal profile generation process.

Its structure is parallel to the electrical generator, but without the final electrical fluctuation step. It:

1. Calls `module_1.build_thermal_daily_profiles(...)`.
2. Applies peak/base factors.
3. Builds the annual calendar.
4. Applies seasonality.
5. Normalizes to 1000 MWh.
6. Scales to annual thermal consumption.
7. Generates a thermal diagram.
8. Saves the thermal profile to Excel.

The output Excel file is saved under:

```text
Generated/load_profiles/
```

with a name similar to:

```text
iDesign_RES_<industry_name>_<country_code>.xlsx
```

### `Modules/module_1.py`: daily profile construction

`module_1` builds the base daily profiles used by the rest of the pipeline.

#### Electrical mode

The electrical function is:

```python
build_electric_daily_profiles(...)
```

It builds one daily profile for each day type:

- weekday,
- Saturday,
- Sunday,
- holiday,
- constant.

Its main operations are:

1. Read normalized end-user profiles from:

   ```text
   Data/ElectricalSpecific/Load_profiles_enduser.xlsx
   ```

2. Read the sheets:

   - `Week_day`,
   - `Saturday`,
   - `Sunday`,
   - `Holiday`.

3. Project legacy end-use profiles into the six electrical categories.

4. Read sector metadata from:

   ```text
   Data/ElectricalSpecific/All_info_industry_types_electrical.xlsx
   ```

5. Read IDEES electrical weights according to `weights_mode`.

6. Expand profiles if `unsummed` mode is selected.

7. Apply work-shift modulation through `module_work_shift`.

8. Multiply each profile column by its weight.

9. Add a `Total` column.

#### Six-category electrical structure

In `summed` mode, the electrical profile uses six categories:

```text
Lighting
Air compressors
Motor drives
Fans and pumps
Low-enthalpy heat
Others (sum mean)
```

These are derived from legacy profiles through a deterministic mapping:

```text
Lighting           <- Lighting
Air compressors    <- Discontinuous mechanical drive
Motor drives       <- Continuous mechanical drive
Fans and pumps     <- Process cooling
Low-enthalpy heat  <- mean(Space heating, Hot water, Process heat)
Others (sum mean)  <- mean(Space cooling, ICT)
```

If some source columns are missing, the code uses zero-valued fallback series or computes the mean over the available columns only.

#### `summed` mode

In `summed` mode, the code reads one sheet per sector from:

```text
Data/General/JRC-IDEES_final_energy_consumption_by_country_summed/
```

Each sector sheet contains the six aggregated rows plus a total row.

The weights are normalized so their sum equals 1.

#### `unsummed` mode

In `unsummed` mode, the code reads detailed sector sheets from:

```text
Data/General/JRC-IDEES_final_energy_consumption_by_country_unsummed/
```

The code searches all sheets matching the sector code. For example, sector `ISI` can match:

```text
ISI
ISI something
ISI-something
ISI_something
```

Detailed rows that match a base profile column use that profile directly. Rows that do not match any base category inherit the shape of `Others (sum mean)` as a fallback approximation.

#### Thermal mode

The thermal function is:

```python
build_thermal_daily_profiles(...)
```

It reads thermal day-type profiles from:

```text
Data/HeatSpecific/Load_profiles_daytypes.xlsx
```

Then it reads final-energy values from the country-specific CSV:

```text
Data/HeatSpecific/industry_heat_eu/industry_final_energy_consumption/industry_final_energy_consumption_<COUNTRY_CODE>.csv
```

The final-energy values are transformed into shares. These shares are applied to the thermal daily profile so each thermal use receives a weighted contribution. A synthetic `data_industry_type` row is created so downstream modules can use the same interface as the electrical pipeline.

Thermal profiles can also be modulated by work shifts.

### `Modules/module_2.py`: peak/base factor adjustment

`module_2` adjusts the daily profiles to reproduce more realistic peak-to-base behavior.

The main function is:

```python
apply_peak_base_factors(...)
```

It receives the five daily profile types built by `module_1`:

- weekday,
- Saturday,
- Sunday,
- holiday,
- constant.

For each profile it:

1. Takes the original `Total` series.
2. Builds a relative total curve by subtracting a reference timestep.
3. Reads the sector `Peak_factor` or `Base_factor`.
4. Scales the total curve.
5. Adds a base level of 100.
6. Redistributes the adjusted total across all applications using the original application shares at each timestep.

The weekday profile uses the peak factor. Saturdays, Sundays, holidays, and constant profiles use the base factor.

The output is a new set of adjusted daily profiles where the global amplitude has been modified, but the internal contribution of each application is preserved proportionally.

### `Modules/module_3.py`: calendar, seasonality, and normalization

`module_3` expands the daily profiles to a full-year series.

#### Annual calendar

The function:

```python
build_load_type_calendar(year)
```

creates a daily calendar for the entire year and classifies each day into one of five load types:

```text
1 = weekday
2 = holiday
3 = Saturday
4 = Sunday
5 = constant
```

The calendar considers:

- weekdays,
- weekends,
- German statutory holidays,
- Epiphany,
- Christmas Eve,
- New Year's Eve,
- bridge days around holidays.

The classification uses neighboring-day logic. For example:

- a non-working day between two working days is treated as a holiday profile,
- a non-working day after a working day and before another non-working day is treated as Saturday,
- a non-working day between two non-working days is treated as constant load.

#### Seasonality

The function:

```python
seasonality(...)
```

concatenates the correct daily profile for each day and applies heating degree day factors at monthly level.

It reads:

```text
Data/ElectricalSpecific/HeatingDegreeDays.xlsx
```

Then it multiplies heating-related demand according to the month:

- `Space heating`, if present,
- otherwise `Low-enthalpy heat`, if present.

This introduces higher heating demand in colder months and lower heating demand in warmer months.

#### Normalization to 1000 MWh

The function:

```python
normalising_1000(df)
```

computes the annual energy from the 15-minute profile:

```text
energy_per_year = sum(Total) * 0.25 / 1000
```

where `0.25` represents 15 minutes in hours.

It then scales all columns so the profile represents exactly **1000 MWh/year**. This creates a standardized intermediate profile that can later be scaled to real annual consumption.

### `Modules/module_4.py`: annual scaling and fluctuations

`module_4` performs the final scaling stage.

#### Annual scaling

The function:

```python
upscale_yearly(year, df_normalized, data_industry_type)
```

looks for an annual consumption column such as:

```text
Energy consumption 2018
Energieverbrauch 2018
```

If the exact year is not available, it searches for available consumption columns and uses the latest supported year.

The normalized profile is multiplied by the annual consumption value, producing a final load profile in kW. Values are rounded to whole kilowatts.

#### Electrical fluctuations

The function:

```python
add_fluctuations(industry_number, df_scaled, data_industry_type)
```

adds random fluctuations to mechanical loads.

The process is:

1. Read the sector fluctuation factor.
2. Find the peak power of the current profile.
3. Scale the fluctuation amplitude according to peak power.
4. Generate normally distributed random noise.
5. Add that noise to mechanical columns.
6. Add the same noise contribution to `Total`.

The function supports several possible column structures:

- legacy columns:
  - `Continuous mechanical drive`,
  - `Discontinuous mechanical drive`,
- six-category column:
  - `Motor drives`,
- fallback column:
  - `Mechanical drives`.

This makes the function compatible with both the original methodology and the updated six-category structure.

## Module `module_work_shift`: industrial work shifts

`module_work_shift` is one of the most important extensions of the project. It introduces an explicit industrial operating schedule into the synthetic profile generation process.

The original methodology used daily profiles that represented typical weekday, Saturday, Sunday, and holiday behavior. However, it did not explicitly represent whether a plant operates in one shift, two shifts, or continuously. In real industrial facilities, demand is strongly affected by operating schedules: production equipment may start before the first shift, reach full operation during the working window, and gradually shut down after production ends.

This module adds that behavior through an activity mask.

---

### Purpose of the work-shift module

The module modifies daily profiles before peak/base adjustment and annual scaling. Its goal is not to change the annual energy allocation, but to redistribute the intra-day shape more realistically.

It answers questions such as:

- Does this sector work only during daytime?
- Does it operate from early morning to evening?
- Does it run continuously 24 hours a day?
- Which loads should strongly follow the production schedule?
- Which loads should remain partially active outside working hours?
- How should start-up and shutdown ramps be represented?

---

### Default shift schedules

The module defines `DEFAULT_SHIFT_SCHEDULES` with three shift types:

```python
DEFAULT_SHIFT_SCHEDULES = {
    "weekday": {
        1: (8, 16),
        2: (6, 22),
        3: (0, 24)
    },
    "saturday": {
        1: (8, 14),
        2: (6, 14),
        3: (0, 24)
    },
    "sunday": {
        1: None,
        2: None,
        3: (0, 24)
    },
    "holiday": {
        1: None,
        2: None,
        3: (0, 24)
    },
}
```

Interpretation:

#### Shift type `1`: one-shift operation

- Weekday: 08:00-16:00.
- Saturday: 08:00-14:00.
- Sunday: inactive.
- Holiday: inactive.

This represents industries with a mainly daytime working pattern.

#### Shift type `2`: two-shift operation

- Weekday: 06:00-22:00.
- Saturday: 06:00-14:00.
- Sunday: inactive.
- Holiday: inactive.

This is the default mode used by the current electrical and thermal generation calls in `module_1`.

#### Shift type `3`: three-shift or continuous operation

- Weekday: 00:00-24:00.
- Saturday: 00:00-24:00.
- Sunday: 00:00-24:00.
- Holiday: 00:00-24:00.

This represents continuous production.

---

### Activity curve

The core idea is the daily activity function:

```text
A_d(t) ∈ [0, 1]
```

where:

- `0` means no scheduled production activity,
- `1` means full scheduled production activity,
- values between `0` and `1` represent ramp-up or ramp-down periods.

The function `_build_activity_curve(...)` creates one activity value per timestep of a daily profile.

For a 15-minute resolution, a day normally contains 96 timesteps. The module does not hard-code 96; instead, it computes the timestep length as:

```python
step_minutes = 24 * 60 / n_steps
```

This makes the function compatible with other daily resolutions as long as the profile covers one full day.

---

### Ramp-up and ramp-down behavior

Industrial consumption does not jump instantly from zero to full activity. For that reason, the module supports two ramp durations:

```text
ramp_up
ramp_down
```

The activity curve is:

```text
0                         outside the shift and ramps
linear increase           during ramp-up
1                         during the active work window
linear decrease           during ramp-down
```

For example, in two-shift mode with a weekday window of 06:00-22:00 and `ramp_minutes=(45, 45)`:

- demand starts ramping up at 05:15,
- reaches full activity at 06:00,
- remains fully active until 22:00,
- ramps down from 22:00 to 22:45,
- then returns to the residual level.

The module also clamps ramps so they do not extend beyond daily boundaries. For example, if the shift starts at 00:00, the ramp-up cannot start before the beginning of the day.

---

### Family defaults

The module includes three industrial family presets:

```text
continuous
batch
assembly
```

Each family provides:

- default ramp-up duration,
- default ramp-down duration,
- default beta values by end use.

#### `continuous`

This family represents industrial processes that tend to keep part of their load active even outside the main working window.

Default ramps:

```text
ramp_up = 120 minutes
ramp_down = 120 minutes
```

Typical beta values are moderate because many loads are only partially schedule-dependent.

#### `batch`

This family represents processes that are more strongly tied to production batches.

Default ramps:

```text
ramp_up = 30 minutes
ramp_down = 30 minutes
```

Mechanical and process loads have high beta values, so they follow the active window more strongly.

#### `assembly`

This family represents production that is highly linked to labor shifts and assembly operations.

Default ramps:

```text
ramp_up = 60 minutes
ramp_down = 60 minutes
```

Lighting and mechanical loads tend to be more sensitive to the working schedule.

---

### Beta sensitivity parameters

Each load column receives a beta value:

```text
β ∈ [0, 1]
```

Beta controls how strongly that load follows the activity curve.

The multiplier applied to each column is:

```text
m(t) = (1 - β) + β · A(t)
```

where `A(t)` is the activity curve.

Interpretation:

- `β = 0`: the column is not affected by the shift schedule.
- `β = 1`: the column fully follows the activity schedule.
- `0 < β < 1`: the column keeps a residual base load outside active hours.

Examples:

- A motor drive with `β = 0.85` drops strongly outside production hours, but does not necessarily disappear completely.
- Lighting with `β = 0.70` follows the working schedule but keeps some residual demand.
- Auxiliary or generic loads with `β = 0.30` are only mildly affected.

---

### How `module_1` uses work shifts

In the electrical pipeline, `module_1` creates a `shift_betas` dictionary after projecting or expanding the daily profiles.

The current default logic is:

```python
if column in {"Motor drives", "Air compressors", "Fans and pumps"}:
    beta = 0.85
elif column == "Lighting":
    beta = 0.70
else:
    beta = 0.30
```

Then it calls:

```python
module_work_shift.apply_work_shifts(
    profiles_weekday,
    profiles_saturday,
    profiles_sunday,
    profiles_holiday,
    shift_type=2,
    family="continuous",
    betas=shift_betas,
    ramp_minutes=(45, 45),
    rescale=True,
)
```

This means the current default electrical behavior is:

- two-shift operation,
- continuous-family baseline,
- 45-minute ramp-up,
- 45-minute ramp-down,
- energy-preserving reshaping enabled.

In the thermal pipeline, a similar call is made with thermal-specific beta values. Most thermal categories use beta around `0.30`, with slightly different values for some electricity-related thermal labels.

---

### Daily energy preservation

A key feature of the module is the `rescale` parameter.

If `rescale=True`, each adjusted column is rescaled so that its daily sum remains equal to the original daily sum.

This is important because the shift module is intended to reshape the profile, not alter the energy weight assigned to that end use.

The algorithm is:

1. Compute the original column sum.
2. Apply the activity multiplier.
3. Compute the adjusted column sum.
4. If the adjusted sum is greater than zero, multiply the adjusted values by:

```text
original_sum / adjusted_sum
```

As a result, the daily temporal distribution changes, but the total daily energy of each application is preserved.

---

### Recomputing the total

After modifying all application columns, the module recalculates:

```text
Total = sum(all application columns)
```

This prevents inconsistencies between individual columns and the total profile.

---

### Custom schedules

The function `apply_work_shifts(...)` also accepts:

```python
schedule_by_day=None
```

If a custom dictionary is passed, it replaces `DEFAULT_SHIFT_SCHEDULES`. This allows the user to define sector-specific or country-specific schedules.

Example:

```python
custom_schedule = {
    "weekday": {1: (7, 15), 2: (6, 20), 3: (0, 24)},
    "saturday": {1: None, 2: (6, 12), 3: (0, 24)},
    "sunday": {1: None, 2: None, 3: (0, 24)},
    "holiday": {1: None, 2: None, 3: (0, 24)},
}
```

Then:

```python
module_work_shift.apply_work_shifts(
    profiles_weekday,
    profiles_saturday,
    profiles_sunday,
    profiles_holiday,
    shift_type=2,
    schedule_by_day=custom_schedule,
)
```

---

### Why the work-shift module matters

The work-shift module makes the generated profiles more realistic because it introduces operational dynamics that are absent from a purely generic daily profile:

- clear distinction between production and non-production hours,
- residual loads outside working windows,
- smooth transitions instead of abrupt steps,
- different behavior for mechanical, lighting, thermal, and auxiliary loads,
- compatibility with one-shift, two-shift, and continuous industries,
- energy preservation before annual scaling.

This allows the model to represent more realistic industrial operation without requiring measured load curves for every sector and country.

## JRC-IDEES helpers

The helper scripts transform raw IDEES industry workbooks into input workbooks that are easier for the load generator to consume.

Raw workbooks must be located in:

```text
Data/General/JRC-IDEES/<COUNTRY_CODE>/
```

---

### `Helpers/parse_unsummed.py`

Despite its name, this helper exports the **summed** six-category workbooks used by `weights_mode="summed"`.

Run it with:

```bash
python Helpers/parse_unsummed.py
```

It writes files to:

```text
Data/General/JRC-IDEES_final_energy_consumption_by_country_summed/
```

with names such as:

```text
DE_final_energy_consumption_summed.xlsx
FR_final_energy_consumption_summed.xlsx
ES_final_energy_consumption_summed.xlsx
```

For each country, the helper:

1. Searches the raw JRC-IDEES country folder.
2. Opens the industry workbook.
3. Finds `_fec` sheets listed in the workbook index.
4. Extracts subsector blocks between market-share and energy-intensity sections.
5. Detects blocks starting at `Lighting` rows.
6. Keeps core variables:

   ```text
   Lighting
   Air compressors
   Motor drives
   Fans and pumps
   Low-enthalpy heat
   ```

7. Groups all other selected variables into:

   ```text
   Others (sum mean)
   ```

8. Aggregates subsectors into one six-row sector representation.
9. Adds a `Total (%)` row.
10. Writes one workbook per country and one sheet per sector.

The aggregation is weighted by active subsector totals. Inactive blocks are skipped or assigned zero contribution, so active sector totals remain normalized.

---

### `Helpers/parse_summed.py`

Despite its name, this helper exports the **unsummed** detailed workbooks used by `weights_mode="unsummed"`.

Run it with:

```bash
python Helpers/parse_summed.py
```

It writes files to:

```text
Data/General/JRC-IDEES_final_energy_consumption_by_country_unsummed/
```

with names such as:

```text
DE_final_energy_consumption_unsummed.xlsx
FR_final_energy_consumption_unsummed.xlsx
ES_final_energy_consumption_unsummed.xlsx
```

This helper preserves more detailed sector and subsector information from the original IDEES workbooks.

It:

1. Reads all country folders under `Data/General/JRC-IDEES/`.
2. Finds the industry workbook for each country.
3. Reads all relevant `_fec` sheets.
4. Extracts market-share blocks.
5. Uses color and row-structure rules to decide which detailed rows should be retained.
6. Writes detailed rows to country-level workbooks.

This format is useful when the user wants to inspect or preserve more detailed IDEES end-use labels instead of collapsing everything into six categories.

---

### Color-based extraction rules

Both helpers rely on row colors in the IDEES workbooks to distinguish parent and detailed rows.

The code defines color groups such as:

```text
parent: blue-like colors
detail: brown-like colors
```

The simplified logic is:

- blue followed by blue: keep the blue row,
- blue followed by brown: keep the following brown detail rows until the next blue row,
- otherwise: keep the current row.

This helps extract meaningful active rows while avoiding duplicated parent/detail aggregation.

## Evaluations and checks

The repository does not rely on a single formal test suite in the generation flow. Instead, the code includes several methodological and runtime checks that help evaluate whether the generated profiles are coherent.

### 1. Configuration validation in `main.py`

Before running the pipeline, `main.py` checks that:

- at least one profile type is enabled,
- `COUNTRY_CODE` is valid,
- `YEAR` is an integer,
- `ELECTRICAL_INDUSTRY_NUMBER` exists,
- `ELECTRICAL_WEIGHTS_MODE` is valid,
- `THERMAL_INDUSTRY_NUMBER` exists when thermal generation is enabled.

This prevents common execution errors caused by invalid user configuration.

---

### 2. Weight normalization

Electrical weights are normalized after reading.

In `summed` mode, the six category values are read and divided by their total.

In `unsummed` mode, detailed weights are averaged across matching active sector sheets and then normalized.

This ensures that the sum of application weights equals 1 before they are applied to daily profiles.

---

### 3. Active-sector filtering

The helper scripts ignore inactive IDEES subsector blocks when aggregating or reading weights. Blocks with zero sector totals do not affect the aggregated result.

This avoids diluting active sector weights with inactive subsectors.

---

### 4. Daily energy preservation in work shifts

When `rescale=True`, the work-shift module preserves the daily energy of each application after applying the shift mask.

This check is important because the shift module should modify the timing of demand, not the total energy assigned to the end use.

---

### 5. Total-column consistency

After weighted profile generation, shift modulation, redistribution, and fluctuation addition, the code recalculates or updates `Total` so it remains consistent with the individual application columns.

---

### 6. Normalization to 1000 MWh

Before final scaling, the annual profile is normalized to 1000 MWh/year. This provides a standard reference profile and makes the scaling stage transparent.

The annual energy is computed from the 15-minute series using:

```text
sum(Total) * 0.25 / 1000
```

---

### 7. Scaling to annual consumption

`module_4` scales the normalized profile to the actual annual energy consumption stored in the sector metadata.

It supports English and German column names:

```text
Energy consumption YYYY
Energieverbrauch YYYY
```

If the requested year is missing, the function can use the latest available consumption column.

---

### 8. Visual evaluation through diagrams

The generated stacked diagrams are an important qualitative evaluation tool. They allow the user to visually inspect:

- whether the daily structure is plausible,
- whether shifts create realistic working windows,
- whether the total profile has reasonable peaks,
- whether the contribution of categories is coherent,
- whether unsummed outputs are too fragmented or dominated by fallback categories.

---

### 9. Suggested manual checks

After generating a profile, it is recommended to verify:

1. The Excel file has a complete datetime index for the year.
2. The time step is 15 minutes.
3. The `Total` column equals the sum of the application columns.
4. The annual energy matches the target consumption.
5. No category has unexpected negative values after fluctuations.
6. The diagram title and file name match the selected country, sector, year, and mode.
7. In `unsummed` mode, detailed labels are meaningful and not excessively dominated by `Others`-like fallback behavior.
